## 二、P9「完整自检」：根因与证据链

### 2.1 先证伪「超时」

原断言只等文案「自检通过（完整…」，失败时 45s 等待把这中间的真实文案吞掉了（上一轮已补
打印）。本轮直接复现 5 次、挂 3 次，失败文案全部一致：

```
完整自检未完成：自检发现问题：malformed inverted index for FTS5 table main.chapter_fts
```

**这是「自检发现问题」，不是「请求超时」**——`fetch` 的 10s 超时文案是
`GET /api/system/integrity?full=1 请求超时（10 秒）`，两者完全不同。

### 2.2 再证伪「库坏了」

失败瞬间做「现场三连」（`window_smoke` 失败分支已固化该诊断）：

| 视角 | 结果 |
|---|---|
| UI 文案 | `自检发现问题：malformed inverted index for FTS5 table main.chapter_fts` |
| 同一接口再发一次 | **ok**（有时仍失败，取决于落到哪条连接） |
| **全新 sqlite3 连接**直接读同一个库文件 | **ok** |
| **同一连接**的第二次 `PRAGMA integrity_check` | **ok** |
| FTS5 自己的核对 `INSERT INTO chapter_fts(chapter_fts) VALUES('integrity-check')` | 通过 |
| 索引行数 vs `chapter` 行数 / `chapter_fts_docsize` | 124 = 124 = 124，无缺失/多余 rowid |
| `engine.dispose()` 后再连 | **ok** |
| 检索结果（`chapter_fts MATCH`） | 修复前后一致，**不受影响** |

结论：**文件是好的**，同一条连接第一次查报错、第二次就好，`dispose()` 后立刻正常 ——
问题在**连接态**，不在数据。

### 2.3 最小复现（可稳定重现）

用两条连接对同一个库：

```text
连接 A：UPDATE chapter …            → 触发器写 chapter_fts（结构进 A 的缓存）
连接 A：SELECT … FROM chapter_fts MATCH …   （或跑一次 integrity_check，确保结构已载入缓存）
连接 B：INSERT INTO chapter_fts(chapter_fts) VALUES('rebuild')  → 换掉整套 FTS5 结构
连接 A：PRAGMA integrity_check      → malformed inverted index   ← 误报
连接 A：PRAGMA integrity_check      → ok                          ← 自愈
```

对照实验：

- 只做「另一连接 UPDATE chapter（触发器写）」**不会**误报 → 日常写作/自动保存不会触发；
- 3 次重复、1 / 10 / 80 章规模均 **3/3 复现** → 与库大小无关，与**是否 rebuild**、以及
  **该连接是否已把 FTS5 结构载入缓存**有关。

机制：SQLite 3.44+ 的 `PRAGMA integrity_check` 会一并校验 FTS5；而 FTS5 的索引结构
（`%_config` 指向的 `%_data` 段表）是 **per-connection 缓存**的。`rebuild` 在连接 B 上换掉
整套结构后，连接 A 仍拿旧结构去对新的索引数据 → 报一条 malformed；A 的这次校验同时把
缓存刷掉，于是第二次就 ok。

### 2.4 为什么 e2e 命中率这么高

`window_smoke` 的 P9 顺序正是 `#42 重建索引` → `#52 完整自检`，中间只隔 500ms 轮询；而
连接池里「跑过 P6 全局搜索（`chapter_fts MATCH`）」的连接正好符合「结构已载入缓存」。
命中哪条连接由池的调度决定，所以表现为 2~3 / 5 的偶发。

## 三、修复

### 3.1 产品侧（根因）

| 文件 | 改动 |
|---|---|
| `backend/database.py` | `integrity_check()` 改为**一次性独立连接**（`sqlite3.connect` → 查 → 关）。完整自检的语义是「校验磁盘上的库」，不该把连接态历史带进结果；`quick_check` 不校验 FTS5，仍走连接池（页面打开热路径） |
| `backend/database.py` | 新增 `recycle_connections()`：`engine.dispose()`，重建索引后调用 |
| `backend/services/maintenance_service.py` | `rebuild_fts()` 提交后 `database.recycle_connections()`，让池内连接全部重新加载 FTS5 结构 |

两层都做：前者保证「自检永远说真话」，后者从源头上不留过期结构（检索虽然不受影响，
但不该把已知的脏状态留在池里）。

### 3.2 回归用例（旧实现下必挂）

`tests/test_settings_maintenance.py` 新增 2 条：

1. `test_integrity_after_fts_rebuild_not_fooled_by_stale_connection` —— 清空连接池 →
   唯一连接「写 + 读」`chapter_fts` → 另一连接 `rebuild` → `integrity_check()`；
   再走 `GET /api/system/integrity?full=1` 复核。
2. `test_rebuild_fts_recycles_connection_pool` —— `rebuild_fts()` 后池内连接数归零。

> 验证方式：临时把 `integrity_check()` 换回「走连接池」的旧实现，第 1 条**必挂**；
> 恢复新实现**必过**。这样这条用例不是摆设。

### 3.3 另外两处时序加固（e2e 侧，不改产品行为）

| 位置 | 旧写法 | 新写法 |
|---|---|---|
| 「代码块格式已应用」 | 设好 DOM 选区后 `sleep(0.3)` 再点工具栏 | 等到 **`activeElement === .ql-editor` 且选区锚点在编辑器内** 再点；失败时 dump 容器数 / 激活元素 / 锚点 / 工具栏 / 页面异常 |
| 「三重编码 + 无障碍：绿色描边」 | 文案出现即读 `getComputedStyle().borderColor` | 先等 `borderColor === rgb(79, 122, 91)`（`--transition-fast` 120ms）再断言 |

脚本不再依赖任何固定 `sleep` 做同步。
