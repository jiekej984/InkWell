## 二、实现过程中的自查发现（8 项）

| # | 发现 | 处置 |
|---|---|---|
| **S2-01** | 任务写「5 个服务模块」，实际需要 **6 个**：枚举要被五个服务同时引用，挂在任一服务上都会循环导入 | 新增 `character_meta.py` 作为唯一来源；文件头注明偏离原因 |
| **S2-02** | **捕获 `IntegrityError` 后直接抛 `ApiError`，session 处于「待回滚」**，调用方继续用会 `PendingRollbackError`（测试直接复现） | 两道防线：① 正常重名**先查重再写**（唯一约束只作兜底）；② 兜底路径 `session.rollback()` 后再抛 |
| **S2-03** | **`promote`（上移一级）把整棵子树的成员都算进冲突检测与计数**——孙子组织里的人若同时在父组织，会被误判冲突导致删除失败 | 改为只取**直属成员**；补回归用例 `test_promote_ignores_grandchild_members` |
| **S2-04** | `list_characters` 传不存在的 `org_id` 时静默返回空列表 | 先 `require_organization` → 报 2001；补用例 |
| **S2-05** | 章节区间校验（存在性 + 起止先后）在成员与关系两处都要用 | 放在 `organization_service.validate_chapter_range`，`relation_service` 复用，避免第二套口径 |
| **S2-06** | 测试里从 `session_scope` 返回 ORM 对象后再访问属性 → `DetachedInstanceError` | 测试改为**会话内断言、只把 id 带出来**；服务返回 ORM 对象的既有约定不变 |
| **S2-07** | 已知取舍：`restore_organization` 递归恢复会连带恢复「父级删除期间被单独删掉的子组织」 | 无删除批次字段无法区分；报告 §5.4 已声明递归恢复语义，留待时间轴版本再细化 |
| **S2-08** | 已知取舍：`list_character_relations` 的 `active` 只看 `to_chapter_id` 是否为空 | 面板展示够用；图数据用**章节位置**精确过滤（`#64` 的 `chapter_id`） |

> S2-02 与 S2-03 是实质缺陷；S2-01 是结构偏离；其余为口径/健壮性修正。

## 四、给 5.3（接口层）的注意点

1. **服务返回 ORM 对象**（角色/立场/组织/关系），接口层要在 `session_scope` 内完成序列化或取字段，不能把对象带出会话。
2. **冲突已由服务层转成 `ApiError(1001)`**，接口层不必再捕获 `IntegrityError`；兜底路径已 `rollback`。
3. **`#54` 元数据直接返回 `character_meta.meta_payload()`**，不要在前端硬编码标签。
4. **图数据是 dict**：`#64` 直接 `ok(graph_service.build_graph(...))`，节点/边/分组已按报告 §6.2 契约命名。
5. **删除组织需要 `strategy`**：`cascade` / `promote`；取消由前端不发请求实现，服务端不处理 `cancel`。
6. **布局并发**：`#81` 把 `GET` 拿到的 `updated_at` 原样回传，服务层比对不一致返回 **3002**。
7. **章节下拉数据**：#76/#77 的 `from/to_chapter_id` 需要章节列表接口（V1 已有 `#17` 卷章树），5.6 直接用。
