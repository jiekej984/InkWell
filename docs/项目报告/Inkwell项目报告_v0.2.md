## 一、项目背景与目标

### 1.1 背景与痛点

写长篇小说的人，今天大致有五类工具可选，但每一类都在长篇场景下有明显缺陷：

| 现有方案                    | 典型问题                                                        |
| ----------------------- | ----------------------------------------------------------- |
| Word / WPS / 记事本        | 没有卷章结构；没有全书字数与进度；单文件过大后卡顿；没有版本历史，只有"另存为 xxx_最终版_真的最终版.docx" |
| 网文平台后台（作家助手等）           | 必须联网；数据存在平台服务器，作者不掌控；与平台强绑定，换平台即换工具；无法离线写作                  |
| Notion / Obsidian 等通用笔记 | 没有"卷-章-字数-版本"的小说领域模型，一切靠模板和插件自己搭；配置成本高于写作收益；字数统计不便          |
| Scrivener 等专业写作软件       | 功能强大但收费、中文语境与汉化支持弱、学习曲线陡峭、不含中文网文工作流                         |
| 零散记录（备忘录、微信、群聊）         | 灵感、设定、人物小传散落各处，写作时找不到，事后要凭记忆重建                              |

**一句话痛点**：长篇作者需要的不是"又一个编辑器"，而是一个**懂小说结构的、数据归自己、不会丢稿、开箱即用的本地工作台**。

### 1.2 目标用户与画像

| 画像                   | 特征                                        | 核心诉求              | V1 服务优先级 |
| -------------------- | ----------------------------------------- | ----------------- | -------- |
| **A. 长篇网文作者**        | 20~~35 岁，日更 3000~~10000 字，常同时开 1~3 本，长期连载 | 写得快、不卡、不丢稿、字数准    | **最高**   |
| **B. 传统/严肃文学与出版向作者** | 重结构与设定一致性，周期长，常有世界观/时间线/人物表               | 设定文档与正文并列管理、长周期可靠 | **高**    |
| **C. 同人/轻小说/爱好者作者**  | 重灵感收集与素材（立绘、场景图）                          | 灵感库、图库            | 低（V2 覆盖） |

**V1.0 明确优先服务 A 与 B 的交集**：即"在长篇、离线、数据自主要求下，需要卷章结构与设定文档的中文作者"。C 的需求推迟到 V2。

### 1.3 核心价值主张（差异化）

Inkwell 只在这四点做到位，其余功能一律不为 V1 让路：

1. **数据主权**：全量数据落在用户自己的 `Documents/Inkwell/`，纯文本/SQLite 可读可拷，卸载不丢、换机即拷。
2. **零配置体验**：一个 exe，双击即用，不需要装 Python、不需要开浏览器、不需要注册账号、不需要联网。
3. **中文长篇领域模型**：卷-章两级结构 + 字数进度 + 设定文档并列 + 章节版本历史，这些是通用笔记工具给不了的。
4. **可扩展与开源**：模块像插件一样加，代码结构清晰，可持续迭代与社区共建。

### 1.4 项目目标与成功标准

**产品目标**：让一位作者能够**从零开始、完整写完一本 30 万字以上的长篇小说**，全程不丢稿、不卡顿、数据可备份可导出。

**V1.0 发布验收标准（可度量，全部满足方可视为发布）**：

| 编号   | 验收标准                                                | 判定方式                         |
| ---- | --------------------------------------------------- | ---------------------------- |
| AC-1 | 支撑单项目 ≥20 卷、≥2000 章、单章 ≤5 万字、全书 ≤500 万字             | 用脚本生成压力数据，实测指标满足 §2.4 性能要求   |
| AC-2 | 冷启动（双击 exe 到窗口可交互）≤ 3s                              | 中位机（i5 + 8G + SSD）实测 5 次取中位数 |
| AC-3 | 打开 5 万字章节到可编辑 ≤ 1s                                  | 同上                           |
| AC-4 | 模拟断电/强杀进程后，最多丢失最近 30 秒内输入                           | 写作中途 `taskkill /F` 后重启验证     |
| AC-5 | 连续写作 1 小时后，仍可回溯到 60 分钟前的任一内容节点                      | 版本历史抽查（对应 §5.3 快照策略）         |
| AC-6 | 可一键导出全书为 TXT 与 Markdown，内容与正文一致                     | 导出后字数与状态栏总字数误差 ≤0.5%         |
| AC-7 | 5 名内测作者完成"导入旧稿 → 写作 → 版本回溯 → 导出"全流程，其中 ≥4 人表示愿意继续使用 | 内测问卷                         |
| AC-8 | 开源仓库中，第三方开发者按 README 可在 30 分钟内跑通开发环境                | 找 1 名未参与开发者计时验证              |

### 1.5 范围界定

**V1.0 范围内（In Scope）**

- 项目基础信息管理（CRUD + 封面 + 标签）
- 卷-章两级大纲与章节写作（富文本）
- 设定文档（世界观/时间线/势力/名词表）
- 自动保存、章节版本历史与回滚
- 字数统计（章节级 + 全书级）
- 全文搜索（章节 + 设定文档）
- 本地备份与恢复、导出 TXT/Markdown
- 回收站（误删恢复）
- Windows 10/11 x64 打包分发

**V1.0 明确不做（Out of Scope）** —— 任何一项被插入 V1，都需走变更流程

- ❌ 云端同步、多人协作、移动端/Web 版
- ❌ 角色库、人物关系图、灵感库、场景图库（→ V2.0~V2.2）
- ❌ AI 情节分析、AI 人物提取（→ V3.0），但 **接口抽象层在 V1 预留**
- ❌ EPUB / DOCX 排版导出（→ V3.1；V1 仅 TXT / Markdown）
- ❌ 账号体系、付费、插件市场
- ❌ macOS / Linux 打包（→ V1.1 评估）
- ❌ 图片 OCR、公式编辑、复杂表格排版
- ❌ 实时协作编辑、评论批注

### 1.6 术语表

| 术语          | 定义                                                         |
| ----------- | ---------------------------------------------------------- |
| **项目 / 作品** | 一部小说，Inkwell 中的最高层级容器                                      |
| **卷**       | 项目下的分卷（如"第一卷·少年篇"），用于组织章节，可选                               |
| **章节**      | 正文的最小组织单元，隶属于某个卷                                           |
| **设定文档**    | 与正文并列的项目级参考资料（世界观、时间线、势力、名词表），不参与字数统计                      |
| **章节版本**    | 章节正文在某时刻的快照，写作中自动生成或用户手动创建。记作"章节版本 #N"，**不**与软件版本号（V1.0）混用 |
| **快照**      | 生成一次章节版本的动作                                                |
| **字数**      | 按 §2.3.1 规则统计的中文字数，**不含** HTML 标签，默认含标点                    |
| **软删除**     | 记录标记为已删除并移入回收站，数据仍在库中，可恢复                                  |
| **数据目录**    | 运行时存放数据库、封面、媒体、备份的根目录，默认 `%USERPROFILE%/Documents/Inkwell` |

### 2.3 关键业务规则

#### 2.3.1 字数统计规则（BR-1）

中文写作场景下"字数"必须明确定义，否则全书总字数会失真：

1. **统计对象**：去除 HTML 标签后的纯文本（`Chapter.content_text` 列，保存时一并计算并缓存）。
2. **CJK 字符**（中日韩统一表意文字、假名、谚文）：逐字计 1。
3. **西文**：按"单词"计，连续字母/数字串计 1（"don't" 计 1，"1998" 计 1）。
4. **标点与空白**：默认**计入**（符合网文平台惯例）；设置项可切换为"不计标点"。
5. **不统计**：HTML 标签、图片、代码块（若有）、设定文档正文、卷名与章节标题。
6. **一致性**：章节字数变化时，异步重算所属卷与项目总字数缓存。

> 规则 4 需在设置中暴露开关，因为不同平台（起点/晋江/番茄）的统计口径不同，作者常需对齐。

#### 2.3.2 自动保存触发规则（BR-2）

"保存"与"快照"是两件事，必须解耦，否则版本表会爆炸：

```
输入停止 3s  → 保存正文（写 Chapter，不生成快照）
距上次保存 ≥30s 且有内容变更 → 强制保存一次
保存成功后 → 按 §5.3 分级策略判断"本次是否值得生成快照"
```

- 保存为**异步、非阻塞**，UI 不卡顿；保存失败时状态栏变红并重试 3 次（退避 1s/3s/9s）。
- 应用关闭、切换章节、窗口失焦时立即强制保存。

#### 2.3.3 排序规则（BR-3）

- `order_index` 采用**间隔步长 1000** 的整型排序，插入时取相邻两者的中值，避免整表批量 UPDATE。
- 当中值用尽（相邻差值 ≤1）时，对当前父节点下的记录做一次局部重整（重排为 1000, 2000, ...）。
- 拖拽排序仅更新被移动项的 `order_index`。

#### 2.3.4 删除与恢复规则（BR-4）

- 所有删除均为**软删除**：置 `is_deleted=1`、`deleted_at=now`，进入回收站。
- 删除项目 → 级联软删除其下的卷、章节、章节版本、设定文档。
- 回收站保留 **30 天**，超过后由启动时清理任务物理删除。
- 恢复项目 → 级联恢复其下未过期的子记录。
- 外键均声明 `ON DELETE CASCADE`，且连接建立时执行 `PRAGMA foreign_keys=ON`。

#### 2.3.5 文件路径规则（BR-5）

- 数据库内一律存**相对于数据目录的相对路径**（如 `covers/project_1.jpg`），避免换机后路径失效。
- 封面与正文图片在写入时进行校验（格式白名单 jpg/png/webp，单张 ≤10MB，超尺寸自动压缩）。
- 删除章节时，其 `media/` 子目录延后到回收站清理阶段才物理删除。

## 三、竞品分析与技术选型

### 3.1 竞品差异化对比

| 产品               | 本地优先     | 卷章领域模型 | 版本历史    | 中文长篇适配        | 费用       | Inkwell 的相对优势   |
| ---------------- | -------- | ------ | ------- | ------------- | -------- | --------------- |
| Word / WPS       | ✅        | ❌      | 弱（靠另存为） | 一般            | 付费/免费    | 领域模型 + 版本历史     |
| 网文平台后台           | ❌（数据在云端） | ✅      | 部分      | ✅             | 免费       | 数据主权 + 离线可用     |
| Notion           | ❌        | ❌（靠模板） | 有       | 一般            | 订阅       | 零配置 + 离线 + 领域模型 |
| Obsidian         | ✅        | ❌（靠插件） | 需插件     | 一般            | 付费商用     | 开箱即用，免配置        |
| Scrivener        | ✅        | ✅      | 有       | 弱（汉化与中文本地化不足） | 付费       | 免费开源 + 中文语境     |
| **Inkwell（目标态）** | **✅**    | **✅**  | **✅**   | **✅**         | **免费开源** | —               |


**结论**：Inkwell 不追求"功能最多"，而是追求"中文长篇小说场景下的最小完整闭环 + 数据主权 + 零配置"。这是它能与上述产品共存而非正面竞争的位置。

### 3.2 技术方案对比

候选方案为"桌面壳 + 前端"的四种主流组合：

| 对比项                  | PyQt / PySide | 本地 Web（用户开浏览器） | **pywebview（选定）** | Electron  |
| -------------------- | ------------- | -------------- | ----------------- | --------- |
| 独立 exe 运行            | ✅             | ❌ 需用户手动开浏览器    | ✅                 | ✅         |
| UI 美观度上限             | 中             | 高              | 高                 | 高         |
| 前端技术栈自由度             | 低（受限于 Qt 体系）  | 高              | 高                 | 高         |
| 打包体积（经验预估·阶段四实测校准）   | 40~70MB       | 20~40MB        | **35~60MB**       | 100~200MB |
| 冷启动（经验预估）            | 1~2s          | 1~2s           | **2~3s**（需拉起本地服务） | 2~4s      |
| 常驻内存（经验预估）           | 150~250MB     | 120~200MB      | **180~300MB**     | 250~400MB |
| 工程化 / 可维护性           | 中             | 高              | **高**             | 高         |
| 团队学习成本（人日，Python 背景） | 5~8           | 1~2            | **2~3**           | 4~6       |
| 适合开源长期迭代             | 中             | 高              | **高**             | 中         |

> 表中数值为**经验预估**，非实测。阶段四须实测并在本表回填真实数据（见决策项 D-06）。

**核心结论**：pywebview 把"网页的 UI 表达力"和"桌面软件的独立体验"结合起来 —— 既不像 PyQt 那样 UI 写起来费劲，也不像浏览器方案那样需要用户手动开浏览器，打包后是一个 exe。代价是需要额外拉起一个本地服务（约 +1s 启动、+60MB 内存），这个代价换来的是**前后端解耦、便于调试、接口可被后续插件/脚本复用**。

### 3.3 技术栈明细（版本已锁定）

| 层级       | 技术                  | 版本要求                          | 用途                                                |
| -------- | ------------------- | ----------------------------- | ------------------------------------------------- |
| 桌面壳      | pywebview           | ≥5.0                          | 原生窗口，加载前端页面；Windows 下使用 Edge Chromium（WebView2）内核 |
| 后端框架     | FastAPI             | ≥0.110                        | REST API，处理数据与业务逻辑                                |
| ASGI 服务器 | uvicorn             | ≥0.27                         | 在子线程中运行 FastAPI                                   |
| 数据库      | SQLite + SQLAlchemy | SQLite 3.35+ / SQLAlchemy 2.0 | 结构化数据存储；FTS5 全文检索                                 |
| 富文本编辑器   | **Quill**           | **2.x**                       | 章节与设定文档编辑（**静态引入、零构建**）                           |
| 前端样式     | 原生 CSS + CSS 变量     | —                             | 简约浅色写作工具风格（不引入 UI 框架）                             |
| 前端脚本     | 原生 ES Module        | —                             | 不引入构建工具，保持"改完即刷新"                                 |
| 打包工具     | PyInstaller         | ≥6.0                          | 打包为 Windows exe（onedir 模式，见 ADR-007）              |
| AI 接口    | 自建抽象层               | —                             | 仅定义接口，V1 不实现任何 Provider                           |

> **关于 Quill 的选型**：v0.1 中"Quill / TipTap 二选一"与"原生 HTML/CSS/JS（无构建链）"是矛盾的 —— TipTap 基于 ProseMirror，必须走 npm 构建，强行引入会推翻整个前端工程假设。因此 **V1 锁定 Quill 2.x**（可 CDN 或本地静态引入、零构建、体积约 60KB gzip、中文文档与社区成熟）。若未来确需 ProseMirror 的能力，须作为独立技术变更，同时引入构建链并重评打包流程。

### 3.4 架构决策记录（ADR）

| ID      | 决策                                  | 备选方案                     | 理由                                         | 主要代价                     |
| ------- | ----------------------------------- | ------------------------ | ------------------------------------------ | ------------------------ |
| ADR-001 | 桌面壳用 pywebview（WebView2）            | PyQt、Electron、Tauri      | UI 表达力 + 独立 exe + Python 团队零学习成本           | 依赖系统 WebView2 Runtime    |
| ADR-002 | 前后端通过本地 HTTP（FastAPI）通信             | pywebview `js_api` 直调    | 接口契约清晰、可独立调试与测试、便于后续插件/脚本复用、与潜在 Web 版共享后端  | 需处理端口分配与安全暴露面（NFR-S1/S2） |
| ADR-003 | 数据用 SQLite 单文件 + WAL                | 纯文件（Markdown 目录）、TinyDB  | 结构化查询、事务、FTS5 全文检索；单文件便于整体备份               | 需自行处理并发与备份               |
| ADR-004 | 富文本用 Quill 2.x（零构建）                 | TipTap、TinyMCE、自研        | 与"原生前端无构建链"一致，静态引入即可用                      | 高级排版能力弱于 ProseMirror     |
| ADR-005 | 正文以 HTML 存储，并冗余 `content_text` 纯文本列 | 存 Markdown、存 JSON(Delta) | HTML 可直接给编辑器回显；冗余纯文本用于字数统计与 FTS5，避免每次去标签   | 写入时需同步维护两列，存储约 +40%      |
| ADR-006 | 版本快照采用分级策略（§5.3）                    | 每次保存都快照                  | 避免版本表爆炸与磁盘膨胀，同时保证可回溯性                      | 自动快照粒度较粗（约 5 分钟）         |
| ADR-007 | PyInstaller **onedir** 模式打包         | onefile                  | onefile 每次启动需解压到临时目录，冷启动可能 +3~8s，违反 NFR-P1 | 分发为文件夹+exe，需打 zip        |

| 层                             | 职责                   | 约束                  |

| 存储层                           | SQLite 文件 + 图片/备份文件  | 路径一律相对数据目录          |

### 4.5 启动与生命周期

```
1. 单实例锁（命名互斥量）→ 已运行则聚焦已有窗口并退出
2. 解析数据目录 → 目录不存在则初始化
3. 检测 WebView2 Runtime → 缺失则弹引导下载页（NFR-C2）
4. 打开数据库 → PRAGMA foreign_keys=ON / journal_mode=WAL / busy_timeout=5000
5. 执行待应用的 migration（schema_version 递增）
6. 启动完整性检查 → 异常则提示从 backups/ 恢复
7. 每日首次启动：创建数据库备份 + 清理过期备份与回收站
8. 选随机空闲端口 → 生成一次性 token → 子线程起 uvicorn
9. 等待 /api/health 就绪（超时 10s 报错退出）
10. 起 pywebview 窗口，加载 index.html 并注入 token
11. 前端拉取 /api/meta → 恢复上次打开的项目与章节（FR-1.5）
12. 退出：强制保存 → 关闭服务 → 释放单实例锁
```

### 5.3 版本快照策略（分级，解决"每 30s 快照 × 保留 50 条"的矛盾）

**问题**：若"每次保存都快照"，一小时写作产生约 120 条；若"最多保留 50 条"，则 25 分钟前的稿子就找不回来 —— 与"不丢稿"目标直接冲突。

**策略**：保存与快照解耦，快照分三类，差异化保留。

| 类型                 | 触发条件                               | 保留规则                          |
| ------------------ | ---------------------------------- | ----------------------------- |
| **auto**（自动）       | 距上次快照 ≥5 分钟 **且** 距上次快照字数变化 ≥200 字 | 保留最近 30 条；此外每日首条自动快照额外保留 30 天 |
| **manual**（手动）     | 用户按 Ctrl+S 或点击"存档"                 | **永久保留**，不参与自动清理              |
| **milestone**（里程碑） | 章节标记为"定稿"，或卷/书完结                   | **永久保留**                      |
| **restore**（回滚）    | 执行回滚前，为当前内容自动建快照                   | 按 manual 规则永久保留               |

**效果测算**：连续写作 1 小时（约 5000 字）→ 生成约 12 条 auto 快照，保留 30 条意味着可回溯约 2.5 小时；配合每日首条（保留 30 天）可回溯一个月内的每日进度。磁盘开销按单章 5 万字、30 条快照计约 1.5MB/章，2000 章约 3GB，需提供"清理某章自动快照"入口。

> 该策略需在阶段二实装后，用 AC-5（1 小时后仍可回溯 60 分钟前的节点）实测校准。

### 5.4 数据库运维

| 项   | 做法                                                                         |
| --- | -------------------------------------------------------------------------- |
| 并发  | 启用 WAL；`busy_timeout=5000`；所有写操作提交到单一 writer 队列，避免 `database is locked`    |
| 完整性 | 每次启动执行 `PRAGMA integrity_check`，失败则阻断启动并引导从 `backups/` 恢复                  |
| 备份  | 使用 `sqlite3.Connection.backup()` 在线热备，避免直接拷贝 WAL 伴生文件造成不一致                 |
| 清理  | 启动时清理：过期备份（>7 日且非周份）、回收站（>30 天）、孤儿媒体文件                                     |
| 迁移  | `app_meta.schema_version` 记录当前版本；`migrate.py` 按顺序应用未执行的迁移脚本，每个迁移须可重复执行（幂等） |

### 5.5 预留扩展表（V2.0+ 建表，扩展点已留好）

### 6.3 关键接口示例

**PUT `/api/chapters/{cid}/content`（自动保存）**

请求：

```json
{
  "content_html": "<p>他推开门……</p>",
  "client_saved_at": "2026-10-21T15:30:00Z",
  "expect_version": 12
}
```

响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "chapter_id": 101,
    "word_count": 3287,
    "project_word_count": 128456,
    "saved_at": "2026-10-21T15:30:01Z",
    "snapshot_created": true,
    "snapshot_version_no": 13
  }
}
```

- `expect_version` 用于乐观锁：服务端当前版本不等于该值时返回 `3002`，防止多窗口覆盖。
- `snapshot_created` 告知前端本次是否触发了快照（§5.3 策略由服务端判定，前端不决定）。

**POST `/api/chapters/{cid}/versions/{vid}/restore`（回滚）**

服务端行为：先把当前正文存为 `change_type='restore'` 的永久快照 → 再用目标版本内容覆盖 `chapter.content` → 重算字数 → 返回新版本信息。全程在一个事务内完成。

## 七、UI/UX 设计方向

### 7.1 设计原则

1. **专注写作优先**：任何装饰性元素都让位于正文区；默认隐藏一切非常用控件。
2. **克制**：只用一种强调色，提示类信息用图标 + 文字，不用大面积色块。
3. **可预期**：破坏性操作必有确认；状态变化必有反馈（保存中 / 已保存 / 失败）。
4. **安静的浅色**：长时间写作不刺眼，对比度满足 WCAG AA。

### 7.4 交互细节

- 状态栏四态：`保存中…`（灰）→ `✓ 已保存 HH:MM`（绿）→ `保存失败，重试中`（红，附重试按钮）→ `离线可用`（无网络时静默）
- 大纲树：右键菜单（重命名/删除/移动/标记定稿）；拖拽时显示插入位置指示线
- 编辑器：粘贴外部内容时自动清理样式，只保留加粗/斜体/标题/列表
- 图片插入：拖拽或按钮 → 复制到 `media/chapter_{id}/` → 插入相对路径
- 首次启动：空状态引导"创建第一本书"，附 3 个示例章节（可一键删除）

## 八、质量保障与工程规范

### 8.1 测试策略

| 层级     | 范围                                      | 目标               |
| ------ | --------------------------------------- | ---------------- |
| 单元测试   | `services/` 全部：字数统计、快照策略、排序重整、备份、导出     | 覆盖率 ≥60%（NFR-M1） |
| 接口测试   | FastAPI TestClient 覆盖 §6.2 全部接口的主路径与错误码 | 主路径 100%         |
| 手工回归清单 | 见下                                      | 每次发布前执行          |

**发布前手工回归清单（必须全绿）**

1. 冷启动计时 ≤3s（AC-2）
2. 连续写作 5 分钟，中途 `taskkill /F`，重启后丢失 ≤30 秒输入（AC-4）
3. 写作 1 小时后，版本历史可回溯到 60 分钟前节点（AC-5）
4. 新建 → 写作 → 删除 → 回收站恢复 → 数据完整
5. 切换章节、跨卷拖动、800 章规模下拉列表不卡（AC-1）
6. 备份 → 手动损坏数据库 → 从备份恢复成功
7. 导出 TXT/Markdown，字数与状态栏误差 ≤0.5%（AC-6）
8. 中文路径、带空格路径下正常读写（NFR-C3）
9. 未安装 WebView2 的机器上给出正确引导（NFR-C2）
10. 重复双击 exe 不会启动第二个实例（NFR-S3）

### 8.2 日志与诊断

- 日志目录 `Documents/Inkwell/logs/`，按天滚动，保留 7 天
- 级别：INFO（启动/备份/导出）、WARNING（保存重试、版本清理）、ERROR（异常栈）
- 设置页提供"打开数据目录"与"导出诊断包"（日志 + 库结构摘要，不含正文）

### 8.3 工程规范

| 项    | 规范                                                              |
| ---- | --------------------------------------------------------------- |
| 分支   | `main`（发布）/ `develop`（集成分支）/ `feature/*`                        |
| 提交   | Conventional Commits：`feat:` `fix:` `docs:` `refactor:` `test:` |
| 代码风格 | Python：`ruff` + `black`；JS：Prettier 默认配置                        |
| 依赖   | `requirements.txt` 锁定小版本，避免打包结果漂移                               |
| 许可证  | 待 D-02 决策，建议 MIT（宽松、利于传播）或 Apache-2.0（含专利条款）                    |
