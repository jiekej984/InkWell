## 一、四类问题的逐项确认

### 1. 目标不清？

| 检查项 | 结论 |

| 产品目标是否有单一陈述 | ✅ §1.4 有明确一句话目标 |

### 2. 需求缺失？

在三轮迭代后仍缺失、且会影响开发启动的：

| 缺失项 | 影响 | 编号 |
|---|---|---|
| **数据目录位于 `Documents/` 与同步盘冲突的风险未识别** | OneDrive 常接管 Documents，会导致 SQLite 被同步占用/半同步损坏，直接冲击"不丢稿"核心承诺 | SC-03（**高风险，必须评估**） |
| **打包可复现性与依赖供应链风险未评估** | 依赖未锁 hash、打包机环境未定，会出现"在我机器上能打包" | SC-04 |
| **换机/迁移的用户流程缺失** | 主推"整体拷贝数据目录"却无步骤与一致性校验 | SC-05 |
| **数据目录不可写时的行为未定义** | 受控文件夹访问/权限不足时静默失败 | SC-08 |
| **日志体积上限与轮转策略未定义** | 长时间运行日志撑满磁盘（与 R-5 同类） | SC-10 |
| **窗口默认/最小尺寸未定义** | UI 实现缺少基准 | SC-12 |

**判定：SC-03（同步盘）是唯一的高危缺失，其余为完善项。**

### 3. 方案自相矛盾？

| BR-9 版本号单调递增 vs §5.3 快照保留 | 一致 | ✅ |
| 术语表 vs 正文用法 | 一致 | ✅ |

### 4. 技术风险未评估？

已评估：R-1~R-13。
**未评估且高概率发生的新风险**：

- **R-14 同步盘/防病毒干扰**：数据目录默认在 `Documents/`，Windows 上常被 OneDrive 接管；同步软件持有文件句柄、产生冲突副本，SQLite 有损坏风险。**这是当前架构下最现实的威胁**，必须给出缓解方案。
- **R-15 长文 + 多图渲染**：5 万字 + 数十张图片的章节，WebView2 渲染与内存压力未评估（R-9 只覆盖纯文本卡顿）。
- **R-16 依赖供应链**：依赖版本号锁定但无哈希校验，打包环境未指定。

**判定：三项未评估，均需补进风险登记册。**

## 二、补全清单（每项含四项内容）

### 2.1 必须修改（SC-01 ~ SC-06）

**SC-01　缺任务级 Definition of Done**
- 问题所在：只有功能级 AC，没有任务级"完成"定义；开发过程中"写完代码"与"可交付"边界模糊
- 影响范围：全部里程碑；验收扯皮、返工
- 修改思路：新增 §8.4 DoD 六条（功能实现/单测/接口文档同步/回归项更新/日志与错误码/CHANGELOG）
- 优先级：**必须修改**

**SC-02　缺"本期明确解决 / 明确不解决"的集中澄清**
- 问题所在：目标陈述分散在 §1.2~§1.5，读者（尤其新接手开发者）无法一眼判断边界
- 影响范围：需求理解一致性
- 修改思路：§1.4 下新增 1.4.1「目标澄清」三栏块：解决 / 不解决 / 推迟到哪版
- 优先级：**必须修改**

**SC-03　同步盘（OneDrive）与防病毒干扰数据目录的风险未评估**
- 问题所在：数据目录默认 `%USERPROFILE%/Documents/Inkwell`，Windows 上 Documents 常被 OneDrive 接管；同步软件在写入期间持有句柄、生成冲突副本，是 SQLite 损坏的高频来源；防病毒/受控文件夹访问也可能拦截写入
- 影响范围：核心承诺"不丢稿"（R-4）；全量用户
- 修改思路：新增 R-14 与缓解措施——① 启动时检测数据目录是否位于已知同步目录（OneDrive/Dropbox/坚果云），是则给出一次性提示并提供"更换目录"入口；② 支持 `INKWELL_DATA_DIR` 与 portable 模式（已有）作为规避手段；③ README 明确声明"请勿将数据目录置于同步盘，或确保应用退出后再同步"
- 优先级：**必须修改**

**SC-04　打包可复现性与依赖供应链风险未评估**
- 问题所在：`requirements.txt` 仅锁定小版本、无哈希；未指定打包机 OS/Python 版本；PyInstaller 构建未声明 `--clean` 与单目录规范
- 影响范围：阶段四；发布产物的可复现性与可信度
- 修改思路：新增 R-16——依赖锁定到补丁版本并附 `requirements.lock`（含 hashes，可用 pip-compile 生成）；打包环境固定为 Windows 10/11 + Python 3.11（**待确认，见 Q-04**）；构建命令固化到脚本
- 优先级：**必须修改**

**SC-05　换机/数据目录迁移的用户流程缺失**
- 问题所在：§4.4 把"整体拷贝数据目录"作为主推迁移方式，但没有任何操作步骤与一致性校验（如拷贝前必须退出应用、拷贝后校验文件完整）
- 影响范围：FR-6 的完整性；用户换机是最容易出数据事故的场景
- 修改思路：新增 FR-6.8「数据目录迁移」与 §12.4「换机迁移步骤」——退出应用 → 拷贝整个目录 → 新机安装同版本或更高版本 → 首次启动自动校验（quick_check + schema_version）→ 不匹配则引导从备份恢复
- 优先级：**必须修改**

**SC-06　启动流程：迁移执行与冷启动 ≤3s 矛盾**
- 问题所在：§4.5 第 6 步在前台渲染前执行迁移；V1 尚无历史版本所以迁移为空，但规范未说明例外，后续首个真实迁移必然击穿 AC-2
- 影响范围：AC-2、NFR-P1；后续每次 schema 升级
- 修改思路：明确 AC-2 **适用于"无待执行迁移的日常启动"**；存在待执行迁移的首启单列为「升级首启」，UI 展示"正在升级数据…"进度，目标 ≤30s（**假设值，待实测**），并计入 R-5/R-14 同类运维风险
- 优先级：**必须修改**

## 三、判定结论

**可以进入开发。**

依据：
1. 目标层：单一目标陈述 + 11 条可度量 AC + 明确 In/Out of Scope（本轮补 1.4.1 集中澄清）。
2. 需求层：7 组功能需求（含优先级）、9 条业务规则、6 类非功能需求均已定义，三轮自审未再发现 Must 级需求缺失。
3. 方案层：架构、数据模型、接口、UI 规范齐备；本轮修复了最后 1 处自相矛盾（迁移 vs 冷启动），并明确 `/files/` 走签名鉴权。
4. 风险层：R-1~R-16 覆盖打包、性能、数据损坏、同步盘干扰、依赖供应链等主要威胁，均有应对措施。
5. 剩余不确定性已全部归类为**可标注假设**（低风险、可推断）与**待确认项**（信息不足，需你确认，我未假设）。

阶段一（骨架）不依赖任何待确认项即可启动。
