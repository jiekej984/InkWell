# 《Inkwell 小说辅助工具 — 项目报告 v0.1》评审意见与改进建议

> 评审对象：Inkwell项目报告.md（v0.1，2026-10-21）
> 评审日期：2026-10-21
> 评审结论：**有条件通过** —— 方向与骨架正确，但需补齐"为什么做/做到什么程度/怎么验收"三块后，方可作为开发契约使用
> 改进成果：同目录下 `Inkwell项目报告_v0.2.md`

---

## 一、总体评价

### 1.1 做得好的地方（应当保留）

| 优点 | 说明 |
|---|---|
| 定位清晰 | "本地运行、数据自主、功能可扩展"三句话把产品边界说清楚了，本地优先的取舍很坚定 |
| 领域模型成型 | 项目 → 卷 → 章 两级结构 + 设定文档并列，符合中文长篇小说的真实写作习惯 |
| 技术选型有对比意识 | 3.2 用四方案对比表论证了 pywebview，不是拍脑袋 |
| 预留扩展有结构感 | 分层目录（api / services）+ 8.1 AI 抽象层 + 8.2 模块化约定，V2/V3 的接入路径是通的 |
| 里程碑有阶段划分 | 骨架 → 功能 → UI → 打包，顺序合理 |

### 1.2 核心判断

v0.1 完成了"需求确认阶段"约 **60%~70%** 的使命：读的人能看懂要做什么、大概怎么做。但它目前更像一份**开发者的设计笔记**，而不是一份**可作为开发契约与验收依据的项目报告**。差距集中在四块：

1. **缺"为什么"** —— 没有痛点、用户、竞品、成功标准。需求的正当性无法被检验，后续所有功能取舍缺乏锚点。
2. **缺"边界与约束"** —— 没有非功能需求、没有 Out of Scope、没有风险登记、没有验收标准。"做完"这件事无法判定。
3. **缺"可执行的细节"** —— API 整章缺失；关键业务规则（字数怎么算、快照怎么生成、排序怎么维护、删除怎么恢复）全部未定；技术选型无量化依据；里程碑无工期。
4. **存在若干内部矛盾与高风险项** —— TipTap 与"原生无构建前端"冲突；自动保存频率与版本保留上限算术上打架；备份/导出被推迟到 V3.1，而数据安全恰恰是写作工具的生命线。

## 二、问题清单

严重级别定义：**高** = 会导致返工、延期或重大缺陷；**中** = 影响质量、可维护性或协作效率；**低** = 规范与体验问题。

### A. 逻辑结构

| ID | 级别 | 位置 | 问题描述 | 影响 | 改进建议 |
|---|---|---|---|---|---|
| P-01 | 高 | 全文开篇 | 缺少"背景与问题定义"。开篇直接是项目名称/定位/设计原则，没有说明目标用户遇到什么问题、现有工具哪里不够好 | 需求优先级无从判断，功能取舍失去锚点 | 新增"项目背景与目标"章节：痛点清单、用户画像、价值主张、成功标准 |
| P-02 | 高 | 2.1 | 缺少范围界定。只说 V1 做什么，没说 V1 明确**不**做什么 | 开发期需求蔓延（V2 角色库随时挤进 V1） | 增加 In Scope / Out of Scope 双清单 |
| P-03 | 高 | 2.1、七 | 缺少验收标准。七个模块均无"做到什么程度算完成" | 阶段二/三/四无法验收，只能靠感觉 | 每个模块配可验证验收条件，并绑定到里程碑 |
| P-04 | 中 | 全文 | 缺少非功能需求章节。性能、可靠性、数据安全、兼容性（WebView2 Runtime）、可维护性零要求 | 做出来的东西可能"能用但难用"，如 10 万字卡顿 | 新增 NFR 小节并给出可量化指标 |
| P-05 | 中 | 全文 | 缺少风险登记册。打包失败、端口占用、编辑器选型、SQLite 单文件损坏等无任何识别与预案 | 风险兑现时无应对，直接冲击工期 | 新增风险表（风险/概率/影响/应对/责任人） |
| P-06 | 中 | 九 | "待确认事项"错位。第 1~3 条（编辑器选型、保存时机、版本条数）本质是技术决策与业务规则，却与"角色库交互细节"混在一起，且均写"开发时再定" | 关键决策被无限期推迟，开发时临时拍板 | 升级为"决策清单"：默认值 + 决策时点 + 责任人 + 影响面 |
| P-07 | 低 | 全文 | 术语不统一：设定文档/文档/世界观混用；"版本: v3"（章节版本）与软件版本 V1.0 混淆 | 沟通与文档引用歧义 | 新增术语表，统一为"章节版本 #N" |
| P-08 | 低 | 文首 | 缺文档元信息与修订记录，只有版本/日期/状态三行 | 无法追踪变更，多人协作易冲突 | 增加文档信息表 + 修订历史表 + 目录（TOC） |

### B. 内容完整性

| ID | 级别 | 位置 | 问题描述 | 影响 | 改进建议 |
|---|---|---|---|---|---|
| P-09 | 高 | 四 | **API 设计整章缺失**。目录里只有 `api/projects.py` 等文件名，无接口清单、请求/响应结构、错误码 | 前后端无法并行开发，也无法联调与验收 | 新增"接口设计"章节：约 30 个接口清单 + 统一响应格式 + 错误码表 |
| P-10 | 高 | 2.1 + 5 + 九.3 | **自动保存与版本快照自相矛盾**："每 30 秒保存 + 每次保存生成快照" + "每章最多保留 50 条" → 一小时写作产生 120 条快照，50 条上限意味着 25 分钟前的稿子就找不回来 | 版本历史形同虚设，违背"不丢稿"初衷 | 明确"保存"≠"快照"；制定分级快照策略（自动/手动/里程碑）+ 差异化清理规则 |
| P-11 | 高 | 2.2 表 | **备份与导出被推迟到 V3.1，风险过高**。V1 只有自动保存，无任何备份/导出/恢复手段；一旦 SQLite 损坏即全稿尽失 | 单点故障 = 全部心血丢失，写作工具最不能犯的错 | 将"每日本地备份（保留 N 份）"与"导出 TXT/Markdown"提到 V1.0 必做 |
| P-12 | 高 | 5.1 | 删除与恢复未定义：项目删除是否级联删卷/章/版本？章节误删能否找回？ | 误操作不可逆，数据安全事故 | 软删除 + 回收站；明确外键级联（ON DELETE CASCADE）与 `PRAGMA foreign_keys=ON` |
| P-13 | 中 | 3.3 | **技术选型内部矛盾**：前端"原生 HTML/CSS/JS（无构建）" vs 富文本"Quill/TipTap"——TipTap 基于 ProseMirror，必须走 npm 构建链 | 选型落不了地，开发中途被迫改架构 | 锁定 Quill 2.x（静态引入、零构建）；若坚持 TipTap，须同时引入构建工具并说明打包方式 |
| P-14 | 中 | 3.1 | 未论证**为何需要 FastAPI 这一层**。pywebview 自带 `js_api`，JS 可直接调 Python，无需 HTTP 服务 | 无谓引入端口占用、安全暴露面、打包复杂度 | 补充 ADR：说明取舍理由，并给出随机端口 + 127.0.0.1 + 单实例锁 + 本地 token 方案 |
| P-15 | 中 | 5.1 | 字段不足以支撑功能：项目缺 status/target_word_count/last_opened_at/last_chapter_id；章节缺 status/summary/content_text；设定文档缺 order_index 与版本历史（与章节不对等）；全表缺软删除 | 无法支撑"写作进度""全文检索""AI 分析""记住上次位置" | 按建议补齐字段，设定文档与章节享受同等版本能力 |
| P-16 | 中 | 5.1 Project.tags | `tags TEXT`（逗号分隔）是反模式：无法精确筛选、无法统计、标签含逗号即出错 | 标签功能不可用 | 改为独立 tag 表（多对多），或退而求其次用 JSON 数组 + 规范化 |
| P-17 | 中 | 2.1 模块二 | **字数统计规则未定义**：是否含标点？是否含 HTML 标签？英文按字符还是单词？ | 网文作者最在意的数字会算错，且全文统计性能差 | 明确规则（去标签纯文本；CJK 逐字计；西文按词计；标点默认计入可配置），并缓存 `content_text` + `word_count` |
| P-18 | 中 | 5.1 order_index | 拖拽排序用连续 INTEGER 需批量 UPDATE 整表，大项目卡顿 | 万章级项目排序性能崩溃 | 采用间隔步长（如 100）或浮点排序，插入取中值，定期重整；建 (volume_id, order_index) 索引 |
| P-19 | 中 | 四 | 数据库运维缺失：未提 WAL、并发写、备份、schema 迁移 | 写冲突、锁死、升级后老数据打不开 | WAL + busy_timeout；写入串行化；`schema_version` 表 + 迁移脚本；定时备份 |
| P-20 | 中 | 全文 | 缺竞品/差异化分析。Notion、Obsidian、Scrivener、作家助手、墨星、Effie 均已存在 | 说不清"凭什么用我" | 新增竞品对比表，明确四项差异化：本地数据主权 + 零配置 exe + 卷章领域模型 + 版本历史 |
| P-21 | 中 | 全文 | 缺测试与质量保障计划，全文无测试、日志、诊断内容 | 质量靠手点，回归成本高 | 新增质量保障章节：单测覆盖 services、关键路径回归清单、日志级别与文件位置 |
| P-22 | 中 | 6.2 vs 2.1 | 搜索在 UI 草图顶栏画了 `[搜索]`，但需求四模块中无此需求 | UI 与需求不一致，功能漏项 | 补齐搜索需求（章节标题 + 正文 + 设定文档全文，SQLite FTS5） |
| P-23 | 低 | 1.3 | 提到"开源友好"但无 License、贡献指南、提交规范、分支模型 | 开源后协作混乱 | 新增工程规范小节（MIT/Apache-2.0、Conventional Commits、main/develop） |
| P-24 | 低 | 全文 | 缺数据导入能力，有存量旧稿（Word/TXT/MD）的作者无法迁入 | 直接劝退存量用户 | V1.1 支持 TXT/Markdown 批量导入并自动拆章 |
| P-25 | 低 | 六 | 写作体感要素缺失：专注/打字机模式、深色模式、快捷键、中文首行缩进 | "能写"但不"好写" | 列入 V1.1，V1 至少保证首行缩进与 Ctrl+S |

## 三、优先改进建议（先做这 10 件）

按"投入产出比 + 阻塞程度"排序，这 10 项做完，报告即可从"设计笔记"升级为"开发契约"：

| 序号 | 改进项 | 对应问题 | 为什么优先 |
|---|---|---|---|
| 1 | 补"背景/痛点/用户画像/竞品差异化" | P-01、P-20 | 决定所有功能优先级的锚点 |
| 2 | 补"成功标准 + Out of Scope" | P-02、P-03 | 让"做完"可判定，防需求蔓延 |
| 3 | 重做自动保存与版本快照策略（分级快照） | P-10 | 现有方案算术上不成立，是核心功能的地基 |
| 4 | 把"备份 + 导出 TXT/MD"提到 V1.0 | P-11 | 数据安全是写作工具的生命线，不能等到 V3.1 |
| 5 | 明确删除/恢复：软删除 + 回收站 + 级联策略 | P-12 | 不可逆误操作是最高频的数据事故 |
| 6 | 新增"接口设计"章节（清单 + 响应格式 + 错误码） | P-09 | 前后端并行与联调的前提 |
| 7 | 补齐非功能需求（性能/可靠性/安全/兼容）与规模假设 | P-04、P-28 | 没有指标就没有优化方向 |
| 8 | 解决 TipTap vs 无构建链的矛盾，锁定 Quill 2.x | P-13 | 架构级矛盾，越晚改代价越大 |
| 9 | 补 ADR：为什么需要 FastAPI 而非 js_api，含端口/安全方案 | P-14 | 明确取舍，避免后期质疑返工 |
| 10 | 新增风险登记册 + 里程碑工作量估算 | P-05、P-29 | 让排期可接受检验 |

其余 32 项（字段补齐、字数规则、排序策略、术语表、格式规范等）已在 v0.2 中逐条落实。

## 四、仍需业务方 / 用户拍板的问题

以下不属于"可以代为假设"的范畴，建议由项目发起人确认后再冻结需求：

1. **首发平台**：V1.0 只做 Windows？macOS 是否需要在 V1.1 内跟上？（当前 v0.2 按"仅 Windows 10/11 x64"编写）
2. **开源策略**：确定开源吗？License 选 MIT 还是 Apache-2.0？仓库是公开还是先私有？
3. **AI 的定位**：V3 的 AI 情节分析是"调用用户自己的 Key"还是"内置服务"？这直接决定 8.1 抽象层的接口签名与成本模型。
4. **目标用户优先级**：优先服务"网文日更作者"还是"传统/严肃文学作者"？两者的痛点权重不同（前者重字数与速度，后者重设定一致性与结构），会影响 V1.1 的功能排序。
5. **验收样本**：内测作者从哪来？是否已有 3~5 位可参与 V1.0 验收的人选？
